# M2 acceptance checklist — one consultation (`c3 consult`) assertions

Derived from `C:\Users\Dmytro\claude-codex-consult` at commit `d592526`. M2 is "one consultation":
a single `c3 consult` run through the `Engine` trait for `codex`, `agy` and `muse` — not panel-of-many
(M4), not the findings/scoreboard tooling (M3), not `c3 providers` itself (M1, already checked in
`m1-acceptance.md`). Every row condenses one or more `Check`/`Say` calls from the plugin's harnesses
into a single assertion group, exactly as `m1-acceptance.md` does (~250 `Check` calls there became
~17 rows; here several thousand lines of harness become the rows below). "Check id" is the harness's
own tag (first argument of `Check`, or the `Say` label) plus a short disambiguator where a tag
repeats. Rows that depend on a verdict already checked in M1 (preflight text/exit code for a single
provider or roster entry) say "see m1-acceptance.md" instead of repeating it.

A C3 `c3 consult` is M2-complete when every row below passes unmodified against the corresponding
harness section (`-Only F02-1`, `-Only RUN` on `harness-engines.ps1`, `-Only ROSTER` on
`harness-muse.ps1`, ... — see the harness/section columns).

Files written per consultation, in C3's own naming (`docs/DESIGN.md` §4, "Files written per
consultation"): `handoffs/<NN>-<engine>-<slug>[-<provider>].md` (header + verbatim/rendered reply),
`.reply.json`, `.events.jsonl`, `.original.md` (after a format repair), `.partial.md` (after a
timeout kill); the plugin's `sessions.json` is C3's ledger store and `findings.json` the findings
store, both under the write lock.

## Open questions

- **Ledger field-order constant duplicated across engines.** `harness-engines.ps1`'s RUN section defines
  the full `$order` string once and asserts codex, agy and muse ledger entries all share it byte-for-byte
  (field names, not values). C3's `c3-core` ledger-entry type should almost certainly derive this order
  from a single struct/serialization order shared by all three `Engine` implementations rather than have
  each engine adapter re-declare it — flagging so the supervisor confirms that's the intended C3 shape
  (one `LedgerEntry` struct regardless of engine) rather than three parallel schemas that happen to agree.
- **Prompt delivery mechanism differs per engine and is load-bearing.** codex/agy read the prompt on
  stdin (agy as one NDJSON line); muse reads it from a FILE (`--prompt-file`) with stdin left EMPTY. This
  is asserted explicitly (`harness-muse.ps1` RUN: "stdin is EMPTY (0 bytes)") and matters for how a C3
  `Engine::run()` implementation composes its subprocess I/O — it is not a detail that can be normalized
  away behind a single "write prompt, read reply" abstraction without also carrying the delivery-channel
  choice per engine.
- **The muse billing/oauth guard is a LAUNCH INVARIANT, not a preflight check, and is re-checked at each
  of: initial launch, right before the guarded process start (a race window), and right before a
  continuation/repair/denial-retry secondary turn.** This is a stronger and more invasive requirement than
  a typical "check credentials once before running" preflight — `Engine` implementations that only expose
  a single `capabilities()`/pre-run credential check will not naturally support the "re-read right before
  every guarded start" semantics F08-1/F09-1/F15-1 require. Flagging for the supervisor to confirm whether
  the `Engine` trait needs an explicit re-check hook invoked at each guarded start, or whether this is
  handled entirely inside the muse engine's own `run()`/`continue()` implementation without a trait-level
  hook.
- **Timeout continuation, denial retry and format repair are three distinct "secondary turn" mechanisms
  with overlapping but not identical gating rules** (continuation is blocked by tree/quota/survivor
  conditions the killed turn's OWN evidence names; denial retry only exists for agy; format repair exists
  for all three but with per-engine prompt/session mechanics). Whether C3 models these as three variants
  of one "secondary turn" abstraction inside each engine, or as genuinely separate code paths per the
  plugin's structure, is a design choice this checklist does not resolve — noting it since the interaction
  rules (e.g. "never more than one continuation," "no continuation after a killed format-repair turn," "a
  killed denial-retry salvages as its own partial-file turn but never becomes a continuation") are easy to
  get subtly wrong if the three are unified too aggressively.
- **`c3 consult` itself does not exist yet** (being implemented in parallel by another worker), so none of
  the rows above has been run end-to-end against a live C3 binary; this checklist is unverified against a
  live binary, exactly as `m1-acceptance.md` was at the time it was written.
