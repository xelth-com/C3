## Framing (before the numbers)

Two premises to challenge:

1. **(A) is two different wins.** "Answered in one line" is achievable inside the scope; "a wake can be skipped" is not: the host's scheduler is out of scope, and a wake whose first act is running `c3 watch` still pays the cached read of the whole context — watch trims the action side only. The skip needs a Monitor or a push, which the brief defers. State the goal as "one-line wakes + event-aligned `--next`", or the design will later be measured against a saving it cannot deliver (finding #1).
2. **(B) "the same contract as the others" borrows words without semantics.** The contract's spine is a killable process tree (timeout/stall/budget → tree kill, recorded). A browser engine's subject is the user's tab, which C3 must not kill. Keep the record chain; replace the kill with an abandon (finding #7).

Unlisted options: (A) an append-only, closed-vocabulary event journal (seq, kind, instant) that every c3 writer appends — the watch answers "since <seq>" exactly and a Monitor has one file to watch (finding #3). (B) a dedicated sandbox process for the adapters — crash isolation from the bridge, at the cost of another moving part.

**Q1.** Fold, by reliability: detached status files *through the judgement* — not mtimes: a killed background leaves `running` on disk and only the pid-liveness judgement derives `died` — worker state tails, the machine health journal (`running` rows, `until`, `retry_after`), the newest ledger entry, quota windows. Cheapest reliable `--next`: min over detached `started + budget_sec`, blocking windows' `resets_at`, health `until`/`retry_after`, and the off-peak start for `off_peak_only` runs — all from files already opened; cap it at the cache-warm interval and the idle threshold, or `--next` itself lets the cache expire or the session overstay the idle rule. Skipped-wake losses: cache TTL expiry (the next turn rewrites the context); a silently dead worker writes nothing (SubagentStop misses it — prior F08-4/F13-4); and `--task` scope misses peer-session replies the coordinator also waits on — offer `--all` over the collab root, like the SessionStart phrase.

**Q2.** B', for three reasons that follow from the rulings: one trust root (C3 verifies the catalogue hashes and owns the deny-by-default API); the extension shrinks to a signed, auditable relay; pacing sits at the send decision point. Minimal host API: `open(url)`, `read(selector|observer)`, `compose(text)`, `send()`, `subscribe(stream)`, `done()`; capabilities `url|read|compose|send`, with `send` additionally gated per adapter by the user's one-time allowance. Caveats: the bridge protocol is itself the real host API (finding #4); "JavaScript allowed" implies a second runtime inside C3 — ship Rust→WASM first, defer JS.

**Q3.** A persisted, crash-safe per-member run record (like the detached status): `prepared → awaiting-user-send → streaming → done | abandoned | timeout | tab-gone`. Record the adapter hash, capabilities granted, mode (draft vs `--send`), pacing events, every send C3 performed, the reply-stream file, and *why* no reply came: user-never-sent (with age) vs budget vs tab closed/navigated. Kill = abandon, recorded before the relay stops (mirror `KillEvent::Before/After`), tab left open, partial salvaged; surface pending drafts in the SessionStart phrase.

**Q4.** Draft-only breaks the retry chain: denial retry, format repair and continuation are re-sends, each needing the user again, and stall/budget timers running while awaiting the user time every draft out (finding #5). Panels serialize on the user's hands — `panel_concurrency` overstates throughput and the adapter+vendor usefulness table partly measures the user's availability (finding #8). The extension/relay trust boundary is unspecified (finding #6).

**What I'd need to choose:** whether the hosts' Monitor can watch a directory (debounce, recursion) — else only `--next` matters; the measured cached-read cost per wake; whether the prior art is MV3 and the target chats expose reply text in the DOM; the size budget for a WASM runtime; how the private plugin pins and updates the extension.
