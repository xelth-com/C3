# Core-contract review
The types and the formatter are solid; the mutation side is not. Fix the store seam before M2c/M3.

**Q1.** Canonicalise-on-write is right: a writer cannot know which host wrote a file, and coexistence needs one fixed shape. But "reads any" is false today - every field of `SessionsFile`/`FindingsFile` is required, so a store from another plugin wave does not parse, and an unmodelled column is dropped and then erased by the canonicalising rewrite (#1, #2). State the contract as: *format* canonical, *schema* tolerant (`#[serde(default)]` + a flattened unknown-capture), plus one legacy fixture per wave.

**Q2.** `plan -> Argv` is the right seam, wrong vocabulary. The plugin's is one turn object with `Mode ∈ {new,resume,fork,denial-retry,timeout-continue,format-repair}` (`codex-consult.ps1:3013`, `:3145`, `:3413`), per-engine `Adapter.{Argv,Stdin,LaunchBlock}`, and one guarded start that re-reads the launch invariant before *every* turn (`codex-consult-common.ps1:687-700`). Minimal change, no redesign: (1) a `TurnKind` covering the three secondary kinds, and gate the agy/muse thread flag on *thread present*, not on `Resume` (`common.ps1:3501`, `:3907`) - today secondary turns lose `--conversation`/`--session-id` (#6); (2) `continue_turn(&Request, &ConversationId)` - `(id, prompt)` cannot carry model/schema/effort/prompt-file, so no continuation argv is buildable; (3) `Capabilities.prompt_delivery: Stdin|NdjsonLine|PromptFile` plus `prompt_via`, `has_usage`, `denial_retry`, `steps_flag`, `modes`, `default_mode` - all already in the plugin table (`common.ps1:3187-3226`); (4) `fn precheck()` for the muse guard; (5) `plan -> Plan{argv: Option<Argv>, stdin, prompt_file}` so `http` is `argv: None`, not an error, plus a pure `cmd_argv_hazard(&Argv)`.

**Q3.** Partly. Newtypes over `String` carry no rules: nothing binds an `AttemptId` to the inputs it repeats and `ConversationId` has no lineage, so "no redraw" and "never cross lineages" are unenforceable here. Cheap now, impossible after M2c: validate the UUID at construction (`UuidRe`, `common.ps1:3516`), put `lineage` on `Request`, add pure `may_resume(caps, thread_lineage, run_lineage)` and `AttemptId::new(consult, inputs_sha256)`. Thread *selection* stays in the runtime.

**Q4.** Do not add ledger columns - the order string is the plugin harness's interop surface. Derived-once is the contract; write it down. Real gaps: `extra` is one slot for records the plugin places at six positions (peak/recovery *before* `Invocation:`; engine turns/warnings/denial retry before `Timeout:`; continuation/partial/failure/status/repair after) and `Range:` is *inside* the timeout line (`codex-consult.ps1:3749-3775`) (#10).

**Q5.** Accept raw `Value` until a fixture pins the shape - but pin each literal before M2 first writes it: what C3 writes becomes the next reviewer's evidence, and key order inside a `Value` is invisible to today's tests. The `denial_retry`/`timeout_continue`/`range` wordings are at `codex-consult.ps1:3759-3764`.

**Q6.** Confirmed: `reviewer.provider_config` (raw) + the `.pack.json` sidecar, no new column. Do not reuse `artifacts[]` - that is the user's `-Artifact` list with a `sha256_after` drift check (`:2496`, `:3915`), so the pack would be scored as a reviewer input that changed mid-run.

**Q7.** Wrong split as written. Deferring *acquisition* is fine; deferring it while `commit()` owns the ordered writes is not - the trait exposes no write-lock handle and no `.reply.json` step, so a runtime must reimplement `commit` to serialise anything (#4). Minimal fix: `take_write_lock(task, timeout) -> WriteLock`, `commit(&WriteLock, ..)`, `write_raw_reply(task, nn, bytes)`. Share modes then stay in a platform impl behind those signatures.

**Q8.** (a) schema tolerance - an unreadable store is a stopped task; (b) the engine table is split across `Capabilities` (4 kinds) and `lineage::ENGINE_NAMES`/`engine_spec` (3) with no `EngineKind -> &str` mapping, so `http` resolves to "unknown engine" and lineage `unknown :: unknown` (#7); (c) no N allocation in the trait (#8); (d) no task-slug validation, so `task_dir` accepts `..\x` or an absolute path (#9); (e) the R12 status file and worktree identity are absent from the code - nothing to review (assumed); (f) cancellation: `child_pid`/`survivors` exist but no trait method acts on them, so recovery is read-only.

## State machines
**FindingStatus** - proposed/implemented/verified/rejected/wontfix/superseded, any to any. Fails: to verified without evidence; to rejected without note; non-proposed to proposed without note; to superseded never fails. Unenforced: the `history[]` append, `superseded_by`, and `from == to` (silent). `status` is pub, so callers bypass `transition` (#11).
**PendingState** - reserved, launching, running, survivors, committing. Enum only: no transition function, no predecessor check, any state deserialises; removal happens at the commit point, single-run path only (#3).
**COMMIT_WRITE_ORDER** - RawReply, TakeWriteLock, ReReadStores, HandoffMarkdown, Findings, Sessions, RemoveRecoveryRecord, Release. ## Verdict: ADVISE

Shapes and byte-level fidelity are sound (I re-verified the 75-key ledger order against the real store), but the store trait cannot express the panel, write-lock or raw-reply steps and the typed readers reject any store written at a different plugin wave, so M2c/M3 would be built on an unserialised commit path.

### Blockers

- **F08-1** `crates/c3-core/src/ledger.rs:48`, `crates/c3-core/src/findings.rs:26` - `SessionsFile`/`FindingsFile` declare every field as required (no `#[serde(default)]`), so C3 cannot read a store written by the plugin at any other schema wave, and cannot read a fresh `findings.json` created by the plugin (which has no `ratings` key). The plugin's own reader tolerates absent properties everywhere. Verify: Add a test that parses `../claude-codex-consult/.collab/bridge-0.2-2026-09-23/sessions.json` into `SessionsFile` and a plugin-created two-key `findings.json` into `FindingsFile`; both currently fail with `missing field`. Remedy: Put `#[serde(default)]` on every non-load-bearing field of `LedgerEntry`, its nested records and `FindingsFile` (declaration order is unaffected, so byte-identity on the c3-design stores is preserved), and add fixtures for at least one older-wave store and a fresh two-key `findings.json`. Document that C3's reader is at least as tolerant as `Get-PropertyValue` with defaults.
- **F08-2** `crates/c3-core/src/ledger.rs:31`, `crates/c3-core/src/store.rs:392` - Unknown columns are silently discarded on read and then permanently destroyed by the canonicalising rewrite: C3 parses into closed structs and writes back only the modelled fields, so in a repository where the plugin and C3 both append to one task, C3 erases any column it does not model. Verify: Parse a store containing one extra top-level column into `SessionsFile`, re-serialise, and diff: the column is absent from the output. Remedy: Add a trailing `#[serde(flatten)] pub unknown: IndexMap<String, Value>` (order-preserving under the already-enabled `preserve_order`) to `LedgerEntry`, `FindingsFile`, `Finding` and the nested records, and assert in `tests/contracts.rs` that a store with an extra column round-trips byte-identically. Then document the rule: C3 never deletes a column it does not understand.
- **F08-3** `crates/c3-core/src/store.rs:354`, `crates/c3-core/src/store.rs:397`, `crates/c3-core/src/store.rs:280` - The panel recovery path is not expressible through `EvidenceStore`: `write_pending` hardcodes the single `.consult.pending.json` path and `commit` removes only that file, while `recover_pending` reads the panel members' `.consult.pending-<NN>.json`. Concurrent panel members clobber one record, and a member's record survives its own commit forever. Verify: Call `FilesStore::write_pending` for two simulated panel members with different `nn`; observe one file on disk. Remedy: Give the trait a pending-path resolver (`fn pending_path(&self, task: &str, nn: Option<u32>) -> PathBuf`) and use it in `write_pending` and in `commit` (pass the record's `nn`, or remove the record the caller names). Add a test that two member records coexist and that committing one removes exactly its own file.
- **F08-4** `crates/c3-core/src/store.rs:358`, `crates/c3-core/src/store.rs:186`, `crates/c3-core/src/store.rs:401` - `FilesStore::commit` does not take `.consult.write.lock`, does not write the `.reply.json` of `WriteStep::RawReply`, and always returns `Ok(0)` for the wait it documents as the write lock's - so the only store-mutating method in the trait contradicts its own doc-comment, and `LedgerEntry.commit_wait_ms` will be recorded as a false 0. Because the trait exposes no lock handle and no raw-reply step, a runtime cannot wrap the encoded order without reimplementing `commit`. Verify: Spawn two threads that each call `FilesStore::commit` on one temp task with a small sleep between `read_sessions` and the rename; observe one entry lost and no `.consult.write.lock` ever created. Keep the platform share-mode open inside `WriteLock`'s constructor so the signature does not change later. Until then, mark `commit` `#[deprecated]`-style in docs as unserialised so no runtime builds on it.
